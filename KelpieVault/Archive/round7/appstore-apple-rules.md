## 2. Required metadata
- **Privacy Policy URL: mandatory for all apps**, regardless of data collected (required since Oct 3, 2018 rule, still in force). Source: https://developer.apple.com/app-store/app-privacy-details/ ; https://www.applaunchflow.com/blog/app-store-support-url-privacy-policy-requirements-2026 (2026).
- **Support URL: mandatory**, must be a real, working contact/support page (not just an email mailto with nothing else). Same sources.
- **Marketing URL: optional.**
- **Category**: pick one primary (Kelpie best fits Developer Tools or Utilities); secondary category optional.
- **Age rating**: Apple overhauled the system in **July 2025**, effective with a hard compliance deadline of **January 31, 2026** — apps not re-completing the questionnaire by that date are blocked from new submissions/updates. New tiers are **4+, 9+, 13+, 16+, 18+** (12+ and 17+ retired); questionnaire adds required questions on in-app controls, capabilities, medical/wellness topics, violent themes. A dev/SSH-console app with no such content should land at 4+. Source: https://developer.apple.com/news/?id=ks775ehf (Apple's own news post, dated 2025, "Updated age ratings in App Store Connect"); corroborated by https://www.macrumors.com/2025/07/25/apple-overhauls-app-store-age-ratings/.
- **Copyright**: free text field, e.g. "© 2026 Anthony Topalides."
- **App Privacy nutrition label**: Apple's own definition (https://developer.apple.com/app-store/app-privacy-details/) — "collect" means transmitting data off-device and retaining it longer than needed to service the request in real time. A **push device token that the relay stores persistently** (to be able to push later) **is retained, not transient — this is "collected"** and should be declared under **Identifiers → Device ID** (and/or "Other Identifiers"), linked to the app's function (not used for tracking). Apple's own example explicitly exempts tokens "sent on a server call and not retained" — Kelpie's relay does retain the token to push later, so that exemption does not apply; declare it. Encrypted notification payload content itself is not readable by the relay (E2E) — if truly opaque ciphertext the relay cannot read, it is defensible to describe as not "collected" in the nutrition-label sense (Apple's label is about identifiable data the developer can access), but note this in review notes since it's a judgment call, not an explicit Apple example. "Contact Info" does not apply (no email/name/phone collected). No analytics/ads means most other categories are "Data Not Collected." Camera (QR) and Photos/Files access used purely on-device (scanning, exporting) with nothing transmitted do not require nutrition-label disclosure — only *collection* (transmission+retention) triggers disclosure, not mere local API access (that's the privacy manifest's job, see Q3). Source: https://developer.apple.com/app-store/app-privacy-details/ (Apple, accessed 2026-09-11).

## 3. Privacy manifest (PrivacyInfo.xcprivacy)
- **Still required in 2026**, mandatory since **May 1, 2024** for all new apps/updates and any third-party SDK embedded. Missing it, or using a "required reason" API category without an approved reason code, causes a **hard rejection at upload/submission**: error **ITMS-91053 "Missing API declaration"** (and a related ITMS-91055 for an invalid/unlisted reason code) — this blocks the binary from processing, it is not a soft warning. Source: Apple Developer Forums thread titles/content referencing ITMS-91053 and TN3183 (https://developer.apple.com/documentation/technotes/tn3183-adding-required-reason-api-entries-to-your-privacy-manifest — Apple's own tech note); https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api (Apple, title resolved via search, body not directly fetchable).
- Relevant required-reason API categories for Kelpie given its described use of UserDefaults (settings), file timestamps (likely if reading/writing files for QR/Files access), system boot time, and disk space: **NSPrivacyAccessedAPICategoryUserDefaults** (needs reason code, e.g. CA92.1 for reading app's own prefs), **NSPrivacyAccessedAPICategoryFileTimestamp**, **NSPrivacyAccessedAPICategorySystemBootTime**, **NSPrivacyAccessedAPICategoryDiskSpace** — each needs one of Apple's enumerated approved reason strings from TN3183; exact codes must be checked against the current TN3183 table before submission (recommend Anthony or a build-focused agent pull the live table, since WebFetch could not retrieve its body in this pass).
- Note: libssh2/OpenSSL vendored as XCFrameworks are third-party code too — if either accesses any required-reason API (e.g., timestamps internally), that SDK's own manifest (or Kelpie's, covering it) must declare it.
- Source: https://developer.apple.com/documentation/technotes/tn3183-adding-required-reason-api-entries-to-your-privacy-manifest (Apple, official, accessed 2026-09-11 — recommend direct re-fetch for the reason-code table).

## 4. Export compliance / encryption
- **`ITSAppUsesNonExemptEncryption = NO` is legitimate for Kelpie** only if its only encryption is "standard" (SSH via libssh2/OpenSSL implementing standard protocols like TLS/SSH is generally treated as exempt "mass-market" / publicly available standard-algorithm encryption, similar to HTTPS via URLSession) — this is Apple's + BIS's long-standing "standard encryption" exemption category. However Kelpie is NOT using only OS-provided encryption (URLSession) — it vendors its own OpenSSL/libssh2 — which commonly still qualifies as exempt under License Exception ENC / 5D992 "mass market" if the crypto is standard algorithms (AES, RSA, EC, TLS/SSH per public standards) and not custom, but this pushes the app into the **"uses encryption, exempt" category** rather than "no encryption," so `ITSAppUsesNonExemptEncryption` should likely be **`NO` if it qualifies for exemption**, but the developer should answer App Store Connect's export-compliance questionnaire truthfully at submission (it asks whether the app uses encryption, whether it's exempt, and may require uploading a **CCATS or self-classification report** or at minimum an **annual self-classification report to the US BIS** for exempt mass-market encryption items — this annual report obligation exists independent of what Apple asks, and is on the developer, not waived by Apple's exemption). Confirmed pattern from multiple forum sources: "encryption built into the operating system ... is exempt from export documentation upload requirements... Apps using exempt forms of encryption might be required to submit a year-end self-classification report to the U.S. government." **This is a legal determination Anthony should not skip** — recommend he consult BIS's EAR §740.17 self-classification guidance directly rather than relying solely on this recon.
- **France still has an additional declaration requirement** for encryption apps distributed there (separate from the US BIS self-classification) — multiple forum threads reference "Export compliance for French distribution" as an ongoing, distinct requirement; App Store Connect's compliance flow surfaces a France-specific question/upload when relevant.
- Apple's own doc (https://developer.apple.com/documentation/security/complying-with-encryption-export-regulations) is the canonical source but returned only its title via WebFetch (JS-rendered) — **recommend a direct browser check of this page** before finalizing the export-compliance answers.
- Sources: https://developer.apple.com/documentation/security/complying-with-encryption-export-regulations (Apple, title only); https://developer.apple.com/forums/thread/725047 ("Export compliance for French distribution"); https://developer.apple.com/forums/thread/121183; general BIS EAR §740.17 background (not Apple-hosted, not separately verified this session).

## 5. Donations / tip jar
- **Guideline 3.1.1**: in-app purchase currencies **may** be used to let users "tip" the developer — this is the compliant in-app mechanism if Anthony wants an in-app tip button. Using IAP is optional, not mandated, if the tip flow lives entirely outside the app.
- **Guideline 3.2.1(vii)**: apps may enable **individual users to give a monetary gift to another individual without IAP**, provided it's optional and 100% goes to the recipient — this covers a plain "support the developer" link/flow as long as it isn't tied to unlocking content/features (if tied to content/features, IAP is required per 3.1.1).
- **External donation links (Ko-fi, GitHub Sponsors, Buy Me a Coffee) inside the app**: Post the **April 30 – May 1, 2025 Epic v. Apple injunction enforcement**, Apple updated guidelines so that in the **US storefront**, apps can include buttons/external links/calls-to-action to external purchase/payment pages **without needing Apple's External Purchase Link Entitlement and without restriction on placement/formatting** — this applies broadly, not just to games, per the court order Apple was found in "willful violation" and ordered to fix immediately. A December 2025 appeals ruling let Apple charge a commission on such external-link purchases but did **not** restore the link ban. **In all storefronts other than the US**, per Apple's own guideline text: "apps and their metadata may not include buttons, external links, or other calls to action that direct customers to purchasing mechanisms other than in-app purchase" **unless** using the region-specific External Purchase Link Entitlement (available in the EU under DMA, and a few other regions Apple lists) — so for **Australia**, external donation links are **not automatically permitted** the way they are in the US; Australia is not currently one of Apple's listed DMA-style entitlement regions, so a Ko-fi/GitHub Sponsors link inside the app risks rejection under 3.1.1 outside the US unless it qualifies as a pure person-to-person gift under 3.2.1(vii) (optional, 100% to recipient, not tied to unlocking anything) — a donation button not gated behind any feature plausibly qualifies globally under 3.2.1(vii) regardless of storefront, which is the safer framing to give App Review in notes.
- **A link to a subreddit is fine** — it is not a purchase/payment link, so 3.1.1/3.2.1 don't apply to it at all.
- Sources: https://developer.apple.com/app-store/review/guidelines/ (Apple, official, quoted verbatim above, accessed 2026-09-11); https://www.macrumors.com/2025/12/11/apple-app-store-fees-external-payment-links/; https://www.neonpay.com/blog/making-sense-of-the-april-30th-2025-epic-v-apple-ruling.

## 7. Review with a server dependency (Guideline 2.1)
- Apple's own guideline text (quoted verbatim, https://developer.apple.com/app-store/review/guidelines/): "...include demo account info (and turn on your back-end service!) if your app includes a login. If you are unable to provide a demo account due to legal or security obligations, you may include a built-in demo mode in lieu of a demo account **with prior approval by Apple**. Ensure the demo mode exhibits your app's full features and functionality."
- Kelpie has no login/account system — it connects to the user's own Mac over SSH, which the reviewer cannot replicate. This is functionally the "unable to provide a demo account" case, but Apple's guideline as written contemplates *login credentials*, not "no server exists for the reviewer to reach at all." Best practice per this text and general App Review norms: **detailed reviewer notes** (App Store Connect's "Notes for Review" field) explaining that the app is an SSH client for a self-hosted developer tool the reviewer cannot access, **plus a demo video** showing full functionality, is the standard workaround — a formal "demo mode with prior Apple approval" would need Anthony to proactively contact Apple Developer Support/App Review beforehand, which he has not indicated he'll do. This session found **no specific 2025–2026 published reports** from other SSH/terminal-client developers about this exact scenario (search returned generic SSH-client roundup/listicle content, not App Review post-mortems) — this is a gap; recommend Anthony search r/iOSProgramming, indie dev forums, or Termius's/Blink Shell's own release notes directly if he wants precedent, since this recon could not surface one.

## 8. Skipping TestFlight
- Confirmed pattern (not from an Apple page with full body text this session, but consistent across Apple Developer Forums and App Store Connect release notes references): a build uploaded to App Store Connect can be **submitted for App Review directly without any TestFlight testing** — TestFlight and App Store submission are independent paths off the same uploaded build; TestFlight external-tester review is a **separate, optional** review only triggered if you distribute via TestFlight to external testers. Going straight to "Add for Review"/submission requires only that the build finish **processing** (a wait period after upload before it's selectable) and that all "Missing Compliance" flags (export compliance, age rating, screenshots, etc.) are resolved — App Store Connect blocks submission, not silently ignores, if compliance info is missing.
- This session could not fetch a full-body Apple Help page confirming the exact current "Add for Review" UI wording for 2025–2026 (developer.apple.com/help pages returned JS-shell only) — recommend Anthony verify directly in App Store Connect at submission time, since Apple has iterated the submission UI multiple times.

## 9. Open-source fork (Apache-2.0 upstream "Heeler")
- **4.1 Copycats**: bars copying another app / minor rebrand-and-pass-off, and bars impersonation or using another developer's icon/brand/product name without approval. Kelpie is Anthony's own fork with a different name, icon, bundle ID, team, and (per CLAUDE.md) a materially different root UI (`HerdrClientRootView` replacing Heeler's own client-first surface) — that's a substantive product difference, not a reskin, which is the right side of 4.1.
- **4.2 Minimum functionality**: not really in play here — Kelpie is a native SwiftUI/SSH app with real functionality, not a wrapped website.
- **5.2 Intellectual Property**: since upstream Heeler is Apache-2.0 (permissive, allows forking/rebranding/redistribution including commercially), there's no IP claim blocking a rebrand as long as license terms (attribution) are honored and Kelpie doesn't imply Apple/Heeler endorsement or reuse Heeler's own name/icon/trademark without permission (5.2.1, 5.2.4). If "Heeler" itself is a registered trademark independent of the Apache license grant (licenses cover copyright, not trademark), Kelpie must not use the Heeler name/branding — CLAUDE.md confirms Kelpie already uses its own name/icon/bundle ID, which is the correct posture.
- **What differentiates enough**: distinct name, icon, bundle identifier, and (per the repo's own docs) a different primary UI/UX (herdr-client-first root screen vs. upstream) — differences beyond cosmetic, satisfying 4.1(a)'s "come up with your own ideas" spirit even though the codebase is a fork.
- **Apache 2.0 attribution, one line**: you must retain the original NOTICE file's attribution notices in redistributions (in a NOTICE file, docs, or displayed credits) and include "a prominent notice stating that you changed the files" wherever you modify Apache-2.0-licensed source, per Apache's own license text (§4).
- Sources: https://developer.apple.com/app-store/review/guidelines/ (4.1, 4.2, 5.2, quoted above); https://www.apache.org/licenses/LICENSE-2.0 (Apache Software Foundation, official license text, §4, accessed 2026-09-11).
