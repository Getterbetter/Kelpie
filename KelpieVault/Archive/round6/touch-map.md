# Touch input scout: sidebar tap and selection handles

## A. Finger tap on herdr's sidebar

Two independent tap handlers fire off the same physical tap; neither is gated on the other.

**Path 1 — Kelpie's click report (fires and IS sent).**
- `HeelerTerminalView.touchesBegan/Moved/Ended/Cancelled` (Sources/Heeler/Terminal/TerminalScreenView.swift:1485-1541) only intercepts touches claimed as a right-button pointer press or a link tap; an ordinary sidebar finger touch is neither, so it is forwarded unchanged into `super.touchesBegan/Ended`.
- Kelpie's own `tapGesture` recognizes independently of that: `gestureRecognizerShouldBegin` (TerminalScreenView.swift:1852-1866) begins it whenever `modeTracker.tracksMouse` is true, which it is for herdr (SGR tracking). `handleTap` → `tapAction` (TerminalScreenView.swift:2346-2388) **always** returns `.report(raisesKeyboard:)` for any tap that isn't a link or momentum-halt — `raisesKeyboard` only toggles whether the keyboard is also requested, not whether `clickTouch(at:)` (TerminalScreenView.swift:1890-1899) runs. So the SGR press+release (`modeTracker.remoteClickSequence`, TerminalMouseReporting.swift:35-59) is sent immediately, `M` then `m` at the same cell, with no prior `mouse_pos` — matching the doc's own quoted trace line.

**Path 2 — the vendored view's own tap-toggle-keyboard, forwarded through Path 1's `super` calls.**
- `UITerminalView.touchesBegan/touchesEnded` (Packages/GhosttyTerminal/.../UITerminalView+Interaction.swift:38-115) arms a `tapCandidate` on `.began` (line 59) and, on `.ended`, if the touch was quick (`tapCandidateMaxDuration` 0.35s) and didn't wander past `tapCandidateSlop` (10pt), unconditionally calls `resignFirstResponder()` or `becomeFirstResponder()` (lines 106-110) — logging exactly the `"tap toggles keyboard"` line quoted in the brief. This logic is **not gated on `modeTracker.tracksMouse`** at all; it runs for every quick direct tap that reaches `super`, which Path 1 guarantees it does.

**Most likely explanation.** The click report is very likely reaching herdr correctly. What "does nothing" visually is that the same tap unconditionally toggles the on-screen keyboard's first-responder state (raising it if hidden, dismissing it if shown) via the vendored package's own logic, independent of and blind to whatever Kelpie's `tapAction`/`keyboardActivationRegion` decided about that same location. A tap on the sidebar (well outside `keyboardActivationRegion`, TerminalScreenView.swift:1846-1853) is told by Kelpie not to raise the keyboard, but the vendored path raises/dismisses it anyway — popping the keyboard over the sidebar (or dismissing an already-open one) on every tap, which reads as "nothing happened" to the workspace switch the user expected, or actively steals the view. Since `tapCandidateArmed` gating only cares about touch count/duration, this fires on **every** direct tap in the terminal, not just the sidebar — the sidebar is simply where the mismatch (herdr expects a click, the view instead flips keyboard state) is most visible because no keyboard interaction was wanted there. This is the double path the brief's own trace hints at (click report + "tap toggles keyboard" for one tap).

Grid mapping (point 3) is not implicated: `TerminalGridPointMapper.cell(at:)` (TerminalMouseReporting.swift:96-106) clamps to `min(max(column,1), columns)`, so a touch left of the origin still resolves to column 1, not 0.

**What a finger drag on the sidebar edge needs, and which gesture is free.** ADR 0016 assigns one-finger drag to local scrolling (`scrollTouch`, gated in `gestureRecognizerShouldBegin` by `abs(velocity.y) > abs(velocity.x)`, TerminalScreenView.swift:1855-1858) and one-finger long-press to a right-click (`remoteRightClickSequence`). A resize needs a press, then a `mouse_pos` **motion report per cell** while held, then a release — the same three-part shape `remoteClickSequence`/`remoteRightClickSequence` already spell for a single point, extended over the drag. The gesture that is free per the ADR is **long-press-then-drag as a left-button drag**: reuse the existing one-finger long-press recognizer (already exclusive with Ghostty's own long-press-for-selection while `tracksMouse`, TerminalScreenView.swift:1875-1880) to send `remoteClickSequence`'s press half on `.began`, follow pan translation with column/row `mouse_pos` motion reports (`isMotion: true`, TerminalMouseEncoding.report, TerminalMouseReporting.swift:35-59) on `.changed`, and the release half on `.ended`/`.cancelled` — mirroring what the trackpad's continuous `sendMousePos`-on-move + `sendMouseButton`-on-press path already does for herdr.

## B. Selection handles

- `TerminalSurface` (Packages/GhosttyTerminal/.../Surface/TerminalSurface.swift) marks only `sendText`, `performBindingAction`, `jumpToPrompt`, and `scrollToRow` `public`. `hasSelection()` (line 227), `readSelection()` (line 237), `readSelectionResult()` (line 241), and `quicklookWord()` (line 310, nested) default to internal — **none are callable from Sources/Heeler**, a separate module.
- `PointerInteractionState.lastSelectionRect` (UITerminalView+Interaction.swift:16) is likewise internal — not visible to the app.
- `UITerminalView` itself is `open` with several `open` selection-adjacent members the app *can* call/override: `selectionMenuPoint(at:)` (UITerminalView.swift:158, already overridden per ADR 0016), `showSelectionCopyMenu(at:)` (line 209), `copySelectedTextToPasteboard()` (line 232), `copy(_:)` (UITerminalView+Interaction.swift:350), and the full `UITextInput`/`UITextInputTraits` conformance (UITerminalView+UITextInput.swift) is `open`.
- **Rectangles (a): not available.** `selectionRects(for:)` (UITerminalView+UITextInput.swift:340-343) unconditionally returns `[]`. `firstRect`/`caretRect` resolve through `TerminalTextInputHandler`'s `markedTextState`/IME facade (TerminalTextInputHandler@UIKit.swift:19-232), not the terminal grid's actual selection — there is no API returning the on-screen rectangle(s) of a word or range selected in the terminal content.
- **Set/extend (b): synthesizable, not exposed directly.** No public `ghostty_surface_set_selection` call is exposed to Swift, and no such symbol appears in this package. What is public/reachable is the same mechanism the trackpad path already uses: `surface.sendMousePos(x:y:mods:)` + a synthesized `ghostty_surface_mouse_button` press/drag/release sequence (both `internal` but callable from within `HeelerTerminalView`'s own subclass code operating on the surface it's given via the delegate/session — same class of call `handleLongPressForSelection` makes at UITerminalView+Interaction.swift:559-566) can drive Ghostty's own click-drag text selection the way a real trackpad drag would, extending a selection cell by cell. This is a synthesis, not a documented "set selection" API.
- **Handles (c): not free — UIKit's real ones don't attach usefully.** `UITerminalView` does conform to `UITextInput` with real `selectedTextRange`/`caretRect(for:)` getters, but they're backed by the linear IME "document" (`TerminalTextInputHandler`/`TerminalMarkedTextState`), not the terminal grid, and — critically — `selectionRects(for:)` always returns `[]`, so `UITextInteraction`/`UITextSelectionDisplayInteraction`, which draw and hit-test handles from those rects, would have nothing to draw or drag against even if attached. Kelpie would have to draw its own handle views and drive them from synthesized mouse drags (per (b)), not from UIKit's selection-display machinery.
- **What exists today:** double-tap-to-select-word is not implemented as a distinct gesture anywhere in this repo or the vendored package (no `numberOfTapsRequired == 2` / "double tap" gesture found outside the unrelated sticky-modifier debounce, TerminalStickyModifierState.swift:23). The one-finger long-press path (`handleLongPressForSelection`, UITerminalView+Interaction.swift:545-606) is what resolves a word via `surface.quicklookWord()` and a local `TerminalSelectionAnchor.resolveRange`, then calls the app's delegate `terminalDidRequestTextSelection` → `TerminalTextSelectionPresenter.present` (Sources/Heeler/Terminal/TerminalTextSelectionPresenter.swift:5-25), which just dumps the resolved text into a **read-only, non-live** `UITextView` sheet (`TerminalTextSelectionViewController`) — it holds a `String` snapshot plus an optional anchor `NSRange`, not a live grid-anchored selection, and offers no extension or drag affordance at all today.

## Follow-up: synthesized mouse events for selection handles

**1. Access (Packages/GhosttyTerminal).**
`TerminalSurface.sendMouseButton`/`sendMousePos` are **internal** (no modifier — same-module default), Surface/TerminalSurface.swift:62-89:
```
func sendMouseButton(state: ghostty_input_mouse_state_e, button: ghostty_input_mouse_button_e, mods: ghostty_input_mods_e) -> Bool
func sendMousePos(x: Double, y: Double, mods: ghostty_input_mods_e)
```
`performBindingAction(_ action: String) -> Bool` is **public** (line 121); `hasSelection() -> Bool` is **internal** (line 227). `UITerminalView.copy(_:)` is **open**: `@IBAction override open func copy(_: Any?)` (UITerminalView+Interaction.swift:350). None of `sendMouseButton`/`sendMousePos`/`hasSelection` are reachable from Sources/Heeler; only `performBindingAction`, `sendText`, `jumpToPrompt`, `scrollToRow` and the `open` view-level members are.

**2. Mouse tracking vs. local selection.**
`handleLongPressForSelection` sends no shift: `surface.sendMousePos(x:y:, mods: ghostty_input_mods_e(rawValue: 0))` (UITerminalView+Interaction.swift:559-564), and never calls `sendMouseButton` at all — it reads `surface.quicklookWord()` directly (line 566), a query that reports the word under a point without a click/report round-trip, sidestepping mouse-tracking capture entirely rather than forcing local selection via shift. No `mouse-shift-capture` (or any mouse-* config key) is set anywhere in `TerminalConfiguration.swift`; the only escape hatch is the untouched `.custom(key:value:)` passthrough (lines 46, 212, 332-333).

**3. Minimal synthesized sequence, and helper availability.**
Because the internal `sendMouseButton`/`sendMousePos` aren't callable from the app, "press A with shift → mouse_pos to B → release" cannot be built from outside the package at all today — there is no public entry point for a synthesized click/drag, shifted or not. If those were made public/open, the sequence would be: `sendMouseButton(state: .PRESS, button: .LEFT, mods: shift)` at A's pixel point, `sendMousePos(x:y:, mods: shift)` per intermediate cell while dragging to B, `sendMouseButton(state: .RELEASE, button: .LEFT, mods: shift)` at B — mirroring the indirect-pointer path's press/move/release shape (UITerminalView+Interaction.swift:190-260). The package does **not** do view-point→cell conversion for callers: only `TerminalGridMetrics`/`InMemoryTerminalViewport`'s public `cellWidthPixels`/`cellHeightPixels` are exposed (Metrics/TerminalGridMetrics.swift:10-16); there is no public `cellForPoint`, so Kelpie's own `TerminalGridPointMapper` (TerminalMouseReporting.swift) remains necessary. Confirmed: `copy(_:)` copies Ghostty's live selection to the pasteboard via `copySelectedTextToPasteboard()` (line 351), and `canPerformAction` gates the Copy menu item on `surface?.hasSelection() == true` (UITerminalView+Interaction.swift:374-380) — so a real selection does exist inside the surface even though the app has no read access to its geometry.
