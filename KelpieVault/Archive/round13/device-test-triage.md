# Triage — seven iPad unit-test failures (commit 8d9234c)

Framing fact: `KelpieVault/Testing status.md:64` says "Round 12c — compiled, not run", and `gh run list` shows CI only ran upstream `main`. None of these seven tests has ever executed anywhere. "Passed on CI" does not cover them.

## 1. PairingScanStoreTests.aRePairedHostSurvivesAnOlderTombstone — (a) real gap, high confidence
`records.read(account: existing.id.uuidString)` returning nil means **no record was ever published for that Host**, not stale state: `records` is `CountingSecretStore` → `VolatileSecretStore` (in-memory, `Sources/Heeler/Transport/SecretStore.swift:30`), defaults are a UUID-named suite removed in `defer`, every other store is in-memory. Failure in 0.002 s (log 17776) rules out timing. No earlier device run can reach it.
Cause: `PairingSync.publish` refuses the write while any tombstone for that Host exists — `Sources/Heeler/Pairing/PairingSync.swift:673-677` (`tombstones[host.id] == nil, syncedTombstone(host.id) == nil`). The round-12c stamp fix (`PairingScanStore.swift:203` `hostEdits.markEdited`) only makes `applyTombstones` (`PairingSync.swift:537-556`) *skip* the defeated tombstone; nothing retires it, so the re-paired Host survives locally but is never republished for up to the 30-day lifetime (`PairingSyncRecord.swift:203`) — the sibling that deleted it never gets it back, and a third device never sees it. The only `records.write` for records is line 681.
Fix: when a tombstone loses to a newer local edit stamp in `applyTombstones`, retire it — `records.removeSecret(account: PairingSyncTombstone.account(for: host.id))` and drop it from the dictionary passed on to `publish` (make the parameter `inout`, or return the surviving set), so publish's concurrent-delete guard and its fresh `syncedTombstone` re-read both see nothing and write the record with `updatedAt = now()`. Keeps `aDeleteDuringPublishNeverWritesTheRecord` green (that tombstone is stamped `now`, so it still out-dates the stamp) and does not contradict `aLocalEditAfterTheDeletionKeepsTheHost`.

## 2. HerdrClientStoreTests.aDetachedClientStillOnScreenOffersAReconnectThatWorks — (a)/test-race, medium-high confidence
The failing wait is "the rejoin should attach again" (log 16541-16543), i.e. `log.recorded.count == 2` never reached. `condition()` there waits for a **second attach** from the rejoined pipeline. Sequence: `reconnect()` → `rejoin()` sets `lifecycleState = .active` synchronously (`HerdrClientStore.swift:236-256`), so `!needsRejoin` passes with no suspension; the replacement is adopted later inside `enqueueLifecycleTransition`. The test's `store.viewDidResize(cols: 80, rows: 24)` (HerdrClientStoreTests.swift:147) therefore lands on the **outgoing** stopped terminal, whose cols/rows are already 80×24 so `AttachTerminalStore.viewDidResize` returns early (`AttachTerminalStore.swift:~300`); the adopted replacement never gets a size and never starts. The suite's other tests wait for `store.terminalID != firstSurface` before resizing — this one does not.
Round-12c's remote-exit change is **not** implicated: the runner throws `sshUnreachable`, which is a transport failure, and `aRemoteExitNamesTheSessionAndWaitsForTheUser` passed.
Fix (test): wait for `store.terminalID` to change after `reconnect()` before calling `viewDidResize`. Product-side hardening worth considering: have `adoptReplacement` seed the replacement with the last reported cols/rows, so a rejoin never depends on SwiftUI delivering a fresh size report (a reused surface geometry would otherwise leave the Client on a permanent "connecting").

## 3. AgentDirectInputTests.composerAndDirectInputTransferVisibleKeyboardWithoutReloading:395 — (b) hardware keyboard, high confidence
Line 395 waits for `inset.height > 0 && (willShowCount > 0 || willChangeFrameCount > 0)` — a real **software** keyboard. With the Magic Keyboard attached iPadOS raises no software keyboard, so the inset stays 0 and it times out (5.114 s, log 14656). Corroboration: `hardwareFirstResponderDoesNotReserveSoftwareKeyboardGap` (line 823) passed, which asserts exactly that absence. Not a product regression; the test needs a software-keyboard precondition or a skip when a hardware keyboard is connected.

## 4-5. terminalReplacementWhileDirectOwnsKeyboardClaimsIntent:1004, dismissAfterReplacementDoesNotRaiseOnSecondReplacement:1072 — (c) test-harness/OS path, medium-high confidence
Both fail on `activateControl` returning false after ~2.29 s (log 14812, 14834) — 2.0 s is exactly `waitForAccessible`'s 40 × 50 ms budget (AgentDirectInputTests.swift:1574-1588), so the `#available(iOS 27, *)` branch (line 1563) was taken and the "Hide Composer" element was never found. These two are the only activateControl tests using the deliberately scene-less `makeLocalTestWindow` (line 1664: `UIWindow(frame:)`, no `windowScene`); the activateControl tests on scene-backed `makeTestWindow` (647, 758, 773) passed. On this OS a scene-less window exposes no accessibility elements, and the `probe:` fallback is only used below iOS 27, so the lookup failure returns false instead of falling back.
Fix (test only): `guard let element = ... else { return probe() }` in `activateControl`, or give these two a scene-backed window.

## 6-7. TerminalStatusDialogTests.theDimOnlyAppliesWhereItIsAskedFor:43, theCardWearsTheTerminalThemeRatherThanTheSystem:58 — (b)/(c) snapshot needs a foreground scene, high confidence
The log emits `[Snapshotting] Rendering a window (…) requires it to be in a foreground scene.` immediately before each failure (log 19565-19567, 19574). `render()` (TerminalStatusDialogTests.swift:88-99) relies on `window.drawHierarchy(in:afterScreenUpdates: true)`, which on device with no foreground scene returns an unrendered (black) bitmap — so the sampled corner is not the red backdrop and the card colour is not the palette mix. Not wide-gamut/colour-space: the sampler uses `CGColorSpaceCreateDeviceRGB` and the deltas are not small. Note `theDialogCoversWhateverTheTerminalWasShowing` "passed" for the same reason — a black pixel satisfies `!= backdrop`; it is a false pass. Pixel snapshots in this suite are simulator-only unless the host app's scene is foreground and the iPad unlocked.
