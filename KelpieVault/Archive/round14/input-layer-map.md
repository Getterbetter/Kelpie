# Input map: iPhone keyboard-dismiss trigger change

Scope covered: Sources/Heeler/Terminal/ (all 23 files), Sources/Heeler/Client/HerdrClientRootView.swift, docs/adr/0016-ipad-pointer-input.md, Sources/Heeler/Terminal grep for GhosttyTerminal-owned recognizers, Tests/ grep.

## 1. Round-12b scroll-to-dismiss
`TerminalScrollKeyboardDismiss.shouldDismiss` — Sources/Heeler/Terminal/TerminalTouchScroll.swift:308-339 (pure logic: travel ≥24pt, `didScroll`, keyboard up, no hardware keyboard, once per gesture). Called from `dismissKeyboardForTouchScrollIfNeeded()` at TerminalScreenView.swift:3141-3164, invoked per-pan-step from `handleHerdrTouchScrollGesture` (TerminalScreenView.swift:3110, `.changed` case around 3120-3125). Dismissal: `dismissKeyboard()` (TerminalScreenView.swift:1440-1444, calls `resignFirstResponder()`) if `isFirstResponder`, else `window?.endEditing(true)` (line 3165, for Console's Direct Input field). NOT iPhone-only in code — `hasHardwareKeyboard` gate (line 767) is the only exclusion; comment at TerminalTouchScroll.swift:312-315 says the trigger exists because "the iPhone keyboard has none [dismiss key]" but nothing restricts it to `UIDevice.userInterfaceIdiom == .phone`. **Flag: contradicts brief's framing of round-12b as iPhone-specific — it currently runs on iPad too whenever no hardware keyboard is attached.**

## 2. Recognizers installed (all in TerminalScreenView.swift)
- `touchScrollGesture` UIPanGestureRecognizer, 1 finger, `cancelsTouchesInView=false`, delegate=self (declared 887, installed 2440-2445). `gestureRecognizerShouldBegin` (1949-1957): refused while `heldPointerDrag != nil`; requires |velocity.y|>|velocity.x|.
- `tapGesture` UITapGestureRecognizer 1-tap/1-touch, `cancelsTouchesInView=false` (895, 2450-2451). Should-begin gate (1962-1975): true if `modeTracker.tracksMouse`, alt screen, momentum running, `keyboardActivationRegion.contains`, or `urlMatchForPress != nil`.
- `doubleTapGesture` UITapGestureRecognizer 2-tap (899, 2467-2469); should-begin always true (1979-1981). No `require(toFail:)` against `tapGesture` — deliberate (comment 2927-2932): first tap always clicks.
- `rightClickGesture` UILongPressGestureRecognizer 1 finger, 0.5s, allowableMovement 10 (914, 2452-2461); fires only `modeTracker.tracksMouse` (1983-1984).
- `textSelectionGesture` UILongPressGestureRecognizer 2 fingers, same timing (918, 2452-2461); fires only `modeTracker.tracksMouse` (1985-1986) — i.e. only while a TUI owns the mouse; otherwise Ghostty's own long press handles selection (1987-1992, generic `UILongPressGestureRecognizer` branch defers to `super.gestureRecognizerShouldBegin` when not tracking mouse).
- `zoomGesture` UIPinchGestureRecognizer (891, 2522-2525) — disables Ghostty's own pinch first.
- `pointerScrollGesture` UIPanGestureRecognizer, indirect-pointer only, non-Catalyst (923, 2496-2507) — trackpad/mouse wheel.
- Delegate `shouldReceive touch` (2014-2022): excludes touches on selection-overlay handles. `shouldRecognizeSimultaneously` (2024-2031): only true for `pointerScrollGesture` (non-Catalyst), false otherwise — i.e. tap/scroll/long-press are mutually exclusive via UIKit's normal one-recognizer-wins arbitration, no explicit `require(toFail:)` pairs.

## 3. Tap resolution path
`handleHerdrTap` (2797-2803) → `handleTap(at:)` (3053-3076): first `urlMatchForPress(at:)` (2317-2320, wraps `linkMatchForPress`→`TerminalSurfaceLinkQuery.match`, text-scan via TerminalLinkDetector then OSC-8 core hit test) — if URL, `open(.url)` calls `onOpenLink?(url)` (2325, wired to `openURL` at 190/293) and **returns, no keyboard action**. Else `tapAction(at:)` (3095-3103): `.haltMomentum` if momentum running; else `.report(raisesKeyboard: keyboardActivationRegion.contains(location) || alt-screen-bottom-band)`. `.report` branch (3068-3073) calls `clickTouch(at:)` then `requestKeyboard()` (1406) if `raisesKeyboard`. Host-path taps are NOT resolved in `handleTap`'s URL branch — comment 3059-3066 explicitly says a path tap is *not* claimed here; it falls through to `tapAction`'s ordinary report/click path, and the path is surfaced instead via the double-tap/two-finger-hold **selection** menu ("Open on Host") — see `onHostPathTap` calls at TerminalScreenView.swift:3002, 3332 (selection-menu action), not from the plain single tap. So today's plain-tap "nothing" branch (no URL, no keyboardActivationRegion, no alt-screen bottom band) still does `clickTouch` + no keyboard raise — it is never a true no-op; there is no tap outcome today that means "resolved to nothing at all."

## 4. Touch selection / hold-drag
Two-finger long press `textSelectionGesture` → `handleHerdrTextSelectionGesture` (2916-2926): on `.began`, haptic, tries `selectWord(at:)` (2947), else presents `TerminalTextSelectionPresenter` full-viewport sheet. One-finger hold `rightClickGesture` → `handleHerdrRightClickGesture` (2821-2892): starts as a held right-click, escalates to a left-button drag once travel exceeds `pointerDragSlop` (max(cellHeight,12)); right-click reports only on `.ended` with no movement. Distinguished from a plain tap purely by UIKit gesture arbitration/timing (0.5s `minimumPressDuration`) — a tap recognizer firing on `.ended` under 0.5s never triggers the long-press recognizers.

## 5. Hardware-keyboard interaction
No branch in `handleTap`/`tapAction` keys off hardware-keyboard presence — tap behavior (link/click/raise-keyboard) is identical with or without one attached. Only the scroll-dismiss gate (`hasHardwareKeyboard`, TerminalScreenView.swift:767, sourced from `hardwareKeyboardProbe` set by the root view's `HardwareKeyboardObserver`, else `GCKeyboard.coalesced`) suppresses dismissal when a hardware keyboard is present. `requestKeyboard()`/`becomeFirstResponder` still runs regardless of keyboard mode; TerminalTextSafety.swift:91-93 separately gates *typed-text* editing actions (`!hasMarkedText, !hasHardwareKeyboard`), unrelated to dismissal.

## 6. Vendored GhosttyTerminal recognizers
`Packages/GhosttyTerminal/Sources/GhosttyTerminal/Platform/UIKit/UITerminalView+Interaction.swift`: its own `touchesBegan` override (line 38), plus 3 internal `UIPanGestureRecognizer`s (lines 395-464, likely scroll/drag-selection/indirect-pointer) and one `UILongPressGestureRecognizer` (line 435, selection) added via its own `addGestureRecognizer` calls; a `shouldBegin`-style check for `UILongPressGestureRecognizer` at line 726. Kelpie's delegate methods on TerminalScreenView do **not** call `require(toFail:)` against any of these — coexistence is entirely through `gestureRecognizerShouldBegin` gating (Kelpie's own recognizers self-refuse per mode/state) and `shouldRecognizeSimultaneously` returning false for everything except the pointer-scroll gesture, so Ghostty's built-ins and Kelpie's run under ordinary single-winner UIKit arbitration, not explicit dependency edges.
